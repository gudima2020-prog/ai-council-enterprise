# AI Studio Enterprise — требования к системе

Версия документа: 0.1

---

## 1. Назначение системы

AI Studio Enterprise — модульная интеллектуальная рабочая среда, объединяющая LLM-модели, агентов, память, документы, криптоаналитику, инструменты разработки и систему расширений в единой платформе.

Система должна быть не просто чат-приложением, а платформой, в которой разные модули используют общее ядро, общий AI Gateway, общую память и единый интерфейс.

---

## 2. Основные пользователи

### 2.1. Основной пользователь

Пользователь, который ежедневно применяет ИИ для:

- анализа криптовалютного рынка;
- программирования;
- работы с документами;
- анализа данных;
- подготовки текстов;
- исследования информации;
- автоматизации задач.

### 2.2. Расширенные пользователи

В будущем система должна позволять подключать:

- разработчиков модулей;
- разработчиков плагинов;
- специалистов по криптоанализу;
- пользователей, работающих с локальными документами и базами знаний.

---

## 3. Главные цели проекта

### 3.1. Единая рабочая среда

Все ключевые ИИ-инструменты должны находиться в одном приложении:

- чат;
- AI Council;
- криптоаналитика;
- документы;
- код;
- исследование;
- память;
- агенты;
- плагины.

### 3.2. Модульность

Каждый крупный функциональный блок должен быть независимым модулем.

Модули не должны напрямую зависеть друг от друга. Взаимодействие должно происходить через ядро, Event Bus, Memory и AI Gateway.

### 3.3. Единый AI Gateway

Все обращения к LLM должны проходить через AI Gateway.

Запрещено делать прямые вызовы OpenRouter, OpenAI, Gemini, Anthropic, Ollama или других провайдеров из бизнес-модулей.

### 3.4. Расширяемость

Платформа должна поддерживать добавление новых модулей и плагинов без переписывания ядра.

### 3.5. Практическая применимость

Каждая версия должна быть рабочей. Не допускается накопление большого объема незапускаемого кода.

## 4. Функциональные требования

### 4.1. Chat Workspace

Система должна поддерживать базовый чат с ИИ.

Минимальные возможности:

- ввод запроса;
- отправка запроса в backend;
- получение ответа;
- выбор режима ответа;
- отображение истории текущей сессии;
- обработка ошибок API.

Расширенные возможности:

- сохранение чатов;
- поиск по чатам;
- экспорт в Markdown, TXT, PDF;
- привязка чата к проекту;
- выбор модели;
- выбор системного промпта.

### 4.2. AI Gateway

AI Gateway должен обеспечивать единую точку доступа к моделям.

Минимальные возможности:

- отправка запроса в OpenRouter;
- настройка модели по умолчанию;
- ограничение max_tokens;
- обработка ошибок провайдера;
- возврат нормализованного ответа.

Расширенные возможности:

- поддержка нескольких провайдеров;
- резервная модель;
- повтор запроса при временной ошибке;
- учет стоимости;
- учет задержки ответа;
- лимиты токенов;
- журнал запросов;
- маршрутизация по типу задачи.

### 4.3. AI Council

AI Council должен позволять получать ответ от нескольких моделей и формировать итоговый вывод.

Минимальные возможности:

- выбор нескольких моделей;
- отправка одного запроса нескольким моделям;
- отображение ответов каждой модели;
- формирование итогового вывода одной моделью-судьей.

Расширенные возможности:

- оценка согласия моделей;
- выявление расхождений;
- оценка уверенности;
- голосование;
- специализированные роли моделей;
- использование разных промптов для разных агентов.

### 4.4. Crypto Platform

Crypto Platform должна стать отдельным модулем платформы.

Минимальные возможности:

- получение рыночных данных;
- отображение базовой информации по торговым парам;
- передача рыночного контекста в AI Gateway;
- анализ торговой ситуации.

Расширенные возможности:

- подключение BingX, Bybit, Binance, OKX;
- сбор свечей;
- индикаторы;
- funding;
- open interest;
- ликвидации;
- стакан;
- новостной фон;
- AI Council для рыночного анализа;
- модуль риск-менеджмента;
- paper trading;
- интеграция с существующим Crypto AI Trader.

### 4.5. Documents Workspace

Система должна поддерживать работу с документами.

Минимальные возможности:

- загрузка PDF, DOCX, XLSX, TXT;
- извлечение текста;
- отправка текста в AI Gateway;
- краткое резюме документа.

Расширенные возможности:

- OCR;
- работа с таблицами;
- поиск по документам;
- сравнение документов;
- извлечение реквизитов;
- генерация ответов и писем;
- локальная база знаний.

### 4.6. Code Workspace

Система должна помогать в программировании.

Минимальные возможности:

- анализ ошибки;
- объяснение кода;
- генерация исправлений;
- работа с фрагментами кода.

Расширенные возможности:

- подключение GitHub;
- анализ проекта;
- генерация патчей;
- локальный code assistant;
- история изменений;
- тестирование.

### 4.7. Research Workspace

Система должна поддерживать исследовательские задачи.

Минимальные возможности:

- постановка исследовательского вопроса;
- структурированный ответ;
- сохранение результатов.

Расширенные возможности:

- web research;
- источники;
- цитирование;
- сравнение данных;
- исследовательские агенты.

### 4.8. Memory

Memory должна быть центральной частью платформы.

Минимальные возможности:

- сохранение истории чатов;
- сохранение запросов и ответов;
- сохранение настроек.

Расширенные уровни памяти:

- Global Memory;
- Project Memory;
- Workspace Memory;
- Session Memory;
- Long-term Memory.

Memory должна позволять находить прошлые решения, документы, выводы, рыночные анализы и использовать их как контекст.

### 4.9. Agents

Система должна поддерживать агентов как независимые сервисы.

Планируемые агенты:

- Chief Agent;
- Crypto Agent;
- Research Agent;
- Code Agent;
- Document Agent;
- Risk Agent;
- News Agent;
- Vision Agent.

Агент должен иметь:

- роль;
- набор инструментов;
- память;
- настройки;
- ограничения;
- журнал действий.

### 4.10. Plugin System

Система должна поддерживать плагины.

Минимальные возможности:

- каталог плагинов;
- загрузка плагина при старте;
- регистрация API-роутов;
- регистрация UI-разделов.

Расширенные возможности:

- Plugin SDK;
- marketplace;
- включение/отключение плагинов;
- права доступа;
- версионирование.

## 5. Нефункциональные требования

### 5.1. Производительность

- Интерфейс не должен зависать во время ответа ИИ.
- Backend должен отвечать на технические endpoints менее чем за 500 мс.
- Долгие задачи должны выполняться асинхронно.
- Большие документы должны обрабатываться по частям.

### 5.2. Надежность

- Ошибки провайдеров должны отображаться понятным текстом.
- Сбой одной модели не должен ломать весь AI Council.
- Ошибка одного модуля не должна останавливать платформу.
- Логи должны позволять восстановить причину ошибки.

### 5.3. Безопасность

- API-ключи не должны попадать в Git.
- .env не должен публиковаться.
- Секреты должны храниться отдельно от кода.
- Логи не должны сохранять секретные ключи.
- Для торговых API должны быть отдельные правила безопасности.
- В будущем необходимо предусмотреть шифрование секретов.

### 5.4. Расширяемость

- Новый модуль должен подключаться без изменения ядра.
- Новый провайдер должен подключаться через AI Gateway.
- Новый агент должен регистрироваться через систему агентов.
- Новый плагин должен подключаться через Plugin Loader.

### 5.5. Кроссплатформенность

Целевые платформы:

- Windows — основной приоритет;
- Linux — перспективная поддержка;
- macOS — перспективная поддержка.

Технологическая база:

- Backend: Python + FastAPI;
- Frontend: React + TypeScript;
- Desktop: Tauri.

### 5.6. Поддерживаемость

- Код должен быть разделен по доменам.
- Модули не должны иметь скрытых зависимостей.
- Документация должна обновляться вместе с изменениями.
- Каждая крупная функция должна иметь описание в документации.

## 6. Технические ограничения

### 6.1. Backend

Backend должен использовать:

- Python;
- FastAPI;
- Pydantic;
- Uvicorn;
- SQLite на ранних этапах.

### 6.2. Frontend

Frontend должен использовать:

- React;
- TypeScript;
- Vite.

### 6.3. Desktop

Desktop-обертка должна использовать:

- Tauri.

### 6.4. LLM

Все LLM-запросы должны проходить через AI Gateway.

На раннем этапе основной провайдер:

- OpenRouter.

В будущем:

- OpenAI;
- Anthropic;
- Google Gemini;
- Ollama;
- LM Studio;
- локальные модели.

---

## 7. Ограничения проекта

- Не реализовывать новую функцию без архитектурного решения.
- Не делать прямые вызовы LLM из модулей.
- Не хранить ключи в коде.
- Не смешивать экспериментальные скрипты с ядром.
- Не добавлять торговое исполнение без отдельного Risk/Security design.
- Не привязывать Crypto Platform к одной бирже.
