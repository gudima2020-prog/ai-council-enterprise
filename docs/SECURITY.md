# SECURITY.md

# AI Studio Enterprise — Security Design

Версия: 0.1  
Фаза: PHASE 0 — Проектирование  
Статус: Draft

---

## 1. Назначение документа

Этот документ описывает архитектуру безопасности AI Studio Enterprise.

Безопасность является критически важной частью платформы, потому что система будет работать с:

- API-ключами LLM-провайдеров;
- ключами криптовалютных бирж;
- локальными документами;
- пользовательской памятью;
- агентами;
- плагинами;
- историей запросов;
- потенциально чувствительными данными.

---

## 2. Главные принципы безопасности

1. Секреты не хранятся в коде.
2. `.env` не публикуется.
3. Логи не должны содержать API-ключи.
4. Все LLM-запросы проходят только через AI Gateway.
5. Плагины работают только через Plugin Context.
6. Агенты не получают прямой доступ к секретам.
7. Торговые операции проектируются отдельно от аналитики.
8. Любое опасное действие требует явного разрешения.
9. Ошибка одного модуля не должна раскрывать секреты.
10. Безопасность проектируется до реализации функции.

---

## 3. Модель угроз

### 3.1. Внешние угрозы

- кража API-ключей;
- перехват сетевого трафика;
- вредоносные плагины;
- компрометация зависимостей;
- подмена ответа внешнего API;
- утечка локальных документов.

### 3.2. Внутренние угрозы

- случайная публикация `.env`;
- запись секретов в логи;
- сохранение приватных данных в Memory без контроля;
- прямой доступ модулей к ключам;
- ошибки в плагинах;
- неконтролируемые действия агентов.

### 3.3. Угрозы Crypto Platform

- использование торгового ключа вместо read-only ключа;
- открытие сделки без подтверждения;
- неправильный риск-менеджмент;
- утечка биржевых ключей;
- выполнение команд вредоносным плагином;
- подмена рыночных данных.

### 3.4. Угрозы Documents Module

- сохранение чувствительных документов без явного понимания пользователя;
- отправка приватного документа во внешнюю LLM;
- неправильное удаление документов;
- утечка персональных данных в логах.

---

## 4. Управление секретами

### 4.1. Ранний этап

На раннем этапе секреты хранятся в `.env`.

Пример:

```env
OPENROUTER_API_KEY=sk-or-v1-...
```

Файл `.env` обязан быть в `.gitignore`.

### 4.2. Запрещено

Запрещено:

- хранить ключи в `.py`, `.ts`, `.json`, `.md`;
- отправлять ключи в чат;
- коммитить `.env`;
- записывать ключи в логи;
- передавать ключи плагинам напрямую.

### 4.3. Будущий этап

В будущем секреты должны храниться через:

- OS Keychain;
- Tauri secure storage;
- encrypted secrets store;
- master password;
- отдельное хранилище биржевых ключей.

---

## 5. Маскирование секретов

Любой вывод, лог или ошибка должны маскировать ключи.

Пример:

```text
sk-or-v1-<redacted>
```

должен отображаться как:

```text
sk-or-v1-abc1************
```

Нужно маскировать:

- OpenRouter keys;
- OpenAI keys;
- Anthropic keys;
- Gemini keys;
- биржевые API keys;
- secret keys;
- access tokens;
- refresh tokens.

---

## 6. AI Gateway Security

AI Gateway является единственным компонентом, которому разрешено работать с LLM-ключами.

Модули отправляют запросы так:

```text
Module -> AI Gateway -> Provider Adapter -> LLM Provider
```

Запрещено:

```text
Module -> OpenRouter
Module -> OpenAI
Module -> Gemini
Plugin -> LLM Provider
Agent -> LLM Provider
```

AI Gateway должен:

- контролировать провайдера;
- контролировать модель;
- ограничивать max_tokens;
- логировать usage без секретов;
- обрабатывать ошибки;
- применять rate limits;
- поддерживать fallback-модели;
- вести статистику стоимости.

---

## 7. Безопасность логов

Логи должны делиться по категориям:

```text
system.log
api.log
llm.log
security.log
crypto.log
agents.log
plugins.log
errors.log
```

В логах запрещено хранить:

- API-ключи;
- secret keys;
- приватные документы целиком без явного разрешения;
- seed phrases;
- пароли;
- приватные токены.

Логи должны хранить:

- время;
- модуль;
- тип события;
- код ошибки;
- краткое описание;
- trace id;
- masked metadata.

---

## 8. Permissions для плагинов

Плагины должны запрашивать разрешения.

Базовые разрешения:

```text
ai_gateway.ask
memory.read
memory.write
events.publish
events.subscribe
documents.read
documents.write
crypto.read
settings.read
settings.write
network.access
files.read
files.write
```

Опасные разрешения:

```text
shell.execute
secrets.read
crypto.execution
files.delete
network.unrestricted
```

Опасные разрешения требуют отдельного подтверждения пользователя.

---

## 9. Plugin Runtime Security

Плагин получает доступ только через Plugin Context.

```python
context.ai_gateway
context.memory
context.events
context.logger
context.settings
```

Плагину запрещено:

- читать `.env`;
- читать секреты напрямую;
- выполнять shell-команды без разрешения;
- открывать сетевые соединения без разрешения;
- менять файлы ядра;
- подменять системные модули.

Если плагин нарушает правила:

1. операция блокируется;
2. событие пишется в security log;
3. плагин может быть отключен.

---

## 10. Agent Security

Агенты не являются полностью доверенными компонентами.

Агент должен иметь:

- роль;
- разрешения;
- scope памяти;
- лимиты инструментов;
- лимиты токенов;
- журнал действий.

Агенту запрещено:

- самостоятельно получать секреты;
- выполнять торговые операции без разрешения;
- удалять документы без подтверждения;
- выполнять shell-команды без отдельного разрешения.

---

## 11. Crypto Platform Security

Crypto Platform требует отдельной политики.

### 11.1. Разделение ключей

Биржевые ключи делятся на:

```text
READ_ONLY
TRADE
WITHDRAWAL
```

Ключи `WITHDRAWAL` запрещены.

Платформа не должна поддерживать ключи с правом вывода средств.

### 11.2. Режимы работы

Допустимые режимы:

```text
ANALYSIS_ONLY
PAPER_TRADING
ASSISTED_TRADING
AUTO_TRADING_SAFE
```

Автоматическое исполнение не реализуется до отдельного Risk/Security design.

### 11.3. Журналирование

Все торговые действия должны логироваться:

- сигнал;
- источник;
- модель;
- риск;
- время;
- параметры;
- статус;
- ошибка.

---

## 12. Documents Security

Документы могут содержать персональные или конфиденциальные данные.

Требования:

- пользователь должен понимать, что документ отправляется во внешнюю LLM;
- большие документы должны обрабатываться частями;
- секреты в документах должны маскироваться, если возможно;
- документы должны иметь статус хранения;
- должна быть возможность удалить документ и связанные chunks;
- OCR-результаты также считаются чувствительными.

---

## 13. Memory Security

Memory может содержать чувствительные данные.

Требования:

- разделение памяти по scope;
- возможность удаления memory item;
- возможность исключить данные из долгосрочной памяти;
- запрет автоматического сохранения секретов;
- теги чувствительности.

Пример sensitivity labels:

```text
public
internal
private
secret
financial
crypto
personal
```

---

## 14. Network Security

Все внешние соединения должны идти через контролируемые сервисы:

- AI Gateway для LLM;
- Exchange Adapter для бирж;
- Research Connector для web;
- Plugin Network API для плагинов.

Плагин не должен произвольно ходить в интернет без разрешения.

---

## 15. Error Handling Security

Ошибки не должны раскрывать:

- ключи;
- пути к чувствительным файлам;
- полный prompt с секретами;
- внутренние токены;
- stack trace в пользовательском интерфейсе.

Пользовательский ответ должен быть понятным.

Подробности — только в защищенном debug log.

---

## 16. Dependency Security

Требования:

- фиксировать зависимости;
- избегать неизвестных пакетов;
- проверять критические библиотеки;
- обновлять зависимости;
- не использовать непроверенный код в плагинах.

---

## 17. Backup Security

Backup может содержать:

- чаты;
- документы;
- память;
- настройки;
- логи.

Требования:

- экспорт без секретов по умолчанию;
- предупреждение при экспорте чувствительных данных;
- возможность шифрованного backup в будущем.

---

## 18. Audit

Платформа должна вести security audit.

События аудита:

- добавлен API-ключ;
- изменён API-ключ;
- удалён API-ключ;
- включён плагин;
- плагин запросил опасное разрешение;
- агент выполнил действие;
- запущен crypto analysis;
- создан trade signal;
- выполнена торговая операция;
- документ отправлен в LLM.

---

## 19. Минимум безопасности для v1.0

К версии 1.0 обязательно:

- `.env` в `.gitignore`;
- запрет прямых LLM-вызовов из модулей;
- AI Gateway как единая точка LLM;
- маскирование ключей в ошибках;
- базовый security log;
- permissions для плагинов;
- запрет withdrawal keys;
- предупреждение перед отправкой документов в LLM;
- централизованная обработка ошибок.

---

## 20. После v1.0

После версии 1.0:

- OS Keychain;
- encrypted secrets store;
- role-based access;
- sandbox для плагинов;
- подпись плагинов;
- advanced audit;
- policy engine;
- шифрование базы;
- secure backup.

---

## 21. Архитектурные запреты

Запрещено:

- хранить ключи в Git;
- логировать секреты;
- давать плагинам прямой доступ к `.env`;
- давать агентам прямой доступ к ключам;
- делать торговое исполнение без Risk/Security design;
- подключать withdrawal keys;
- отправлять документы во внешнюю LLM без явного понимания пользователя.
